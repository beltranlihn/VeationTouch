# Slamtec RPLIDAR S2E: hardware, Ethernet protocol, SDK, third-party libraries, touch-wall field issues

Method note: primary sources were downloaded and read as text (Slamtec bucket PDFs, GitHub raw files, GitHub API). The Chinese S2E protocol PDF and Chinese datasheet lost their CJK text during extraction, but tables, hex values and field names were readable. The English datasheet v1.8 (robu.in mirror) could not be fetched (DNS failure), so datasheet numbers come from the Slamtec product spec page and the Chinese datasheet v1.5. Date of research: 2026-11-14.

## 1. Official S2E specifications

### Takeaway
S2E: 32,000 samples/s, nominal 10 Hz, 0.1125° angular resolution, 30 m @90% / 10 m @10% reflectivity, 0.05 m blind range, ±30 mm accuracy, 905 nm Class 1, IP65, 9–28 V DC (12 V typical), >2 W, Ethernet UDP 10/100M. Motor speed is adjustable (a 15.14 Hz reading appears in the manual); the S-series spec is otherwise identical across S2L/S2/S2P/S2E except range and interface.

### Inferences
- At 32,000 sps / 10 Hz, one revolution has about 3,200 samples, i.e. about 0.11° per sample. At 3 m range the lateral spacing is about 5.9 mm, at 5 m about 9.8 mm (derived: arc = r × 0.1125° in radians). Finger-sized objects are therefore covered by several returns up to ~5 m.
- Because blind range is 5 cm, the scan plane can hug the wall (a few cm in front) without the sensor's own blind zone mattering for a top-center mount, except directly below the sensor housing.
- "±1.5° scan field flatness" is the plane tilt: over a 3 m wall this is up to ±78 mm of plane deviation from the nominal plane (derived: 3000 × tan 1.5°), which matters for a plane that must stay a few cm from the wall. Mounting-time per-unit calibration of tilt is essential. The "negative/positive pitch" model variants (R1E vs R2E) indicate the tilt is skewed to one side per variant; our unit code is S2M1-R2E (positive pitch 0°–1.5°) per the v1.5 datasheet, so the plane tilts away from horizontal in one direction only.

### Gaps
- Beam divergence / spot size at distance: not found in any document read (the datasheet text available did not contain it).
- MTBF, startup/spin-up time (seconds), IP65 connector details, exact lux rating from the official datasheet: not found. The English datasheet v1.8 could not be fetched.
- Differences vs S3/newer models (S3, C1, etc.): not researched in depth; the SDK README lists A1, A2, A3, S1, S2, S3, C1, T1 as supported.
- Motor speed adjustable range for S2E: manual shows 15.14 Hz as an example and the SDK has `LidarMotorInfo{min_speed,max_speed}` and `getMotorInfo`/`setMotorSpeed`, but the actual numeric limits for S2E were not found.

## 2. Ethernet communication protocol

### Takeaway
S2E is a UDP server (default 192.168.11.2:8089); the host sends 0xA5-framed requests and receives 0xA5 0x5A-descriptor responses. Three scan modes exist (Standard, DenseBoost, Sensitivity); Sensitivity mode (HQ nodes, 96 per packet) carries a per-packet device timestamp in microseconds. IP is changed with RoboStudio/FrameGrabber "IP Config" or SDK `setLidarIpConf` and requires a reset. Heartbeat/keepalive behaviour is undocumented.

### Cited Findings
- Transport: "The host system communicates with SLAMTEC LIDAR via the Ethernet, which using UDP protocol. LIDAR plays a role as the UDP server" — [LR001 lidar protocol v1.0 en](https://bucket-download.slamtec.com/1cb3edd319c0fee6922fc5962e7765e887eccc36/LR001_SLAMTEC_lidar_protocol_v1.0_en.pdf). The S2E protocol PDF is the same document family (rev 1.0, 2022-04-22, covers "LPX T1" and "S" series Ethernet) — [S2E protocol v1.0 cn](https://bucket-download.slamtec.com/29ed73b84370f1ff1e3c09022b79976b46c6558f/SLAMTEC_rplidarkit_protocol_S2E_v1.0_cn.pdf)
- Default IP 192.168.11.2; host NIC must be on the same subnet but must not use that IP ("The user Ethernet address cannot be the same as that of RPLIDAR S2E"). The Windows steps in the manual show setting the PC's address in 192.168.11.x; RoboStudio manual connect: "Udp Server" mode, IP 192.168.11.2, port 8089 — [S2E user manual v1.0 en](https://bucket-download.slamtec.com/5350555d005bfd7a8685fcea6e80e9edb764adb1/SLAMTEC_rplidarkit_usermanual_S2E_v1.0_en.pdf). (The manual's Windows step text literally says to set the PC to 192.168.11.2, an apparent typo that contradicts its own earlier warning; use another address, e.g. 192.168.11.5.)
- SDK UDP port 8089; the older Slamtec "ethernet module" variant used TCP port 20108: "ultra_simple --channel --udp <ip> [port] ... Port number 8089"; "--tcp ... Port number 20108" — [LR002 SDK manual v2.0 en](https://wiki.slamtec.com/download/attachments/83066883/LR002_SLAMTEC_rplidar_sdk_v2.0_en.pdf?api=v2). TCP is for the serial-to-Ethernet module, not for the S2E's native interface per this manual.
- Contradiction on S2E TCP: Slamtec's Interactive Toolkit manual says for Ethernet LiDAR "Enter the IP address and port number corresponding to the LIDAR and select TCP mode" — [RPLIDAR Interactive Toolkit manual](https://wiki.slamtec.com/download/attachments/83066883/RPLIDAR%20Interactive%20Toolkit%20Instruction%20Manual%20-%20V1.1.pdf?api=v2), whereas the S2E manual and datasheet say UDP, port 8089. Not resolved; treat UDP 8089 as authoritative for S2E and verify TCP on hardware.
- The SDK manual's code sample for UDP incorrectly shows `createTcpChannel("192.168.11.2",8089)` (documentation typo) — [LR002 SDK manual v2.0 en](https://wiki.slamtec.com/download/attachments/83066883/LR002_SLAMTEC_rplidar_sdk_v2.0_en.pdf?api=v2)
- Discovery: RoboStudio "Auto Discovery to Lidar..." and FrameGrabber "Auto-Discovery" use "the device discovery function of RPLIDAR S2E"; on Windows this requires Bonjour ("If Bonjour has been installed on Windows (the SDK directory contains the installation package bonjour.rar)... wait 2 to 3 seconds") — [S2E user manual v1.0 en](https://bucket-download.slamtec.com/5350555d005bfd7a8685fcea6e80e9edb764adb1/SLAMTEC_rplidarkit_usermanual_S2E_v1.0_en.pdf). This implies mDNS/DNS-SD (Bonjour); the exact service name was not found (inference).
- Changing IP: RoboStudio/FrameGrabber "Command > IP Config" then reset the device; SDK: `setLidarIpConf`, `getLidarIpConf`, `getDeviceMacAddr` ("Set LPX and S2E series lidar's static IP address") — [S2E user manual v1.0 en](https://bucket-download.slamtec.com/5350555d005bfd7a8685fcea6e80e9edb764adb1/SLAMTEC_rplidarkit_usermanual_S2E_v1.0_en.pdf); [sl_lidar_driver.h](https://raw.githubusercontent.com/Slamtec/rplidar_sdk/master/sdk/include/sl_lidar_driver.h)
- Request framing: little endian; request = `0xA5`, 1-byte command, 1-byte payload size, 0–255 payload bytes, 1-byte checksum (only when payload present; XOR of all previous bytes, "checksum = 0 ... XOR"). Response descriptor: `0xA5 0x5A`, 30-bit length + 2-bit send mode (0x0 single, 0x1 multiple response), 1-byte data type — [S2E protocol v1.0 cn](https://bucket-download.slamtec.com/29ed73b84370f1ff1e3c09022b79976b46c6558f/SLAMTEC_rplidarkit_protocol_S2E_v1.0_cn.pdf)
- Commands (byte values): STOP 0x25 (no response, wait 100 ms), RESET 0x40 (no response, wait ~1 s), SCAN 0x20 (descriptor `A5 5A 05 00 00 40 81`, 5-byte nodes), EXPRESS_SCAN 0x82 (payload 5 bytes: working_mode + 4 reserved; request `A5 82 05 WM 00 00 00 00 C`), GET_INFO 0x50 (descriptor `A5 5A 14 00 00 00 04`, 20 bytes: model, fw minor/major, hw, 16-byte serial), GET_HEALTH 0x52 (descriptor `A5 5A 03 00 00 00 06`: status 0 good / 1 warning / 2 error, 16-bit error code), GET_SAMPLERATE 0x59 (4 bytes: Tstandard, Texpress in µs), GET_LIDAR_CONF 0x84 (payload type u32 + data; response `A5 5A S 00 00 00 20`), MOTOR_SPEED_CTRL 0xA8 (payload u16 Rpm) — [S2E protocol v1.0 cn](https://bucket-download.slamtec.com/29ed73b84370f1ff1e3c09022b79976b46c6558f/SLAMTEC_rplidarkit_protocol_S2E_v1.0_cn.pdf); [LR001 protocol en](https://bucket-download.slamtec.com/1cb3edd319c0fee6922fc5962e7765e887eccc36/LR001_SLAMTEC_lidar_protocol_v1.0_en.pdf)
- GET_LIDAR_CONF types: 0x70 SCAN_MODE_COUNT (u16), 0x71 US_PER_SAMPLE (u32, q8), 0x74 MAX_DISTANCE (u32, q8), 0x75 ANS_TYPE (u8: 0x81 SCAN, 0x82 dense EXPRESS, 0x83 HQ EXPRESS), 0x7C TYPICAL (u16), 0x7F NAME (string) — [S2E protocol v1.0 cn](https://bucket-download.slamtec.com/29ed73b84370f1ff1e3c09022b79976b46c6558f/SLAMTEC_rplidarkit_protocol_S2E_v1.0_cn.pdf). Slamtec "highly recommends users manipulate work modes of an LIDAR via the LIDAR Public SDKs" — [LR001 protocol en](https://bucket-download.slamtec.com/1cb3edd319c0fee6922fc5962e7765e887eccc36/LR001_SLAMTEC_lidar_protocol_v1.0_en.pdf)
- Standard SCAN node (5 bytes): byte0 quality[7:2] + !S + S; byte1 bit0 C(=1) + angle_q6[6:0]; byte2 angle_q6[14:7]; bytes3-4 distance_q2 (little endian). angle = angle_q6/64.0 deg; distance = distance_q2/4.0 mm; S=1 marks start of a new 360° scan — [S2E protocol v1.0 cn](https://bucket-download.slamtec.com/29ed73b84370f1ff1e3c09022b79976b46c6558f/SLAMTEC_rplidarkit_protocol_S2E_v1.0_cn.pdf)
- Dense (DenseBoost) capsule: descriptor `A5 5A 54 00 00 40 85` (84-byte packets). Packet: sync1 high nibble 0xA + ChkSum[3:0]; sync2 high nibble 0x5 + ChkSum[7:4]; start_angle_q6 (16 bits, bit 15 = S start flag); then 40 cabins of 2 bytes, each a 16-bit distance in mm (0 = invalid). Checksum = XOR of the packet bytes. Angles are not transmitted per sample, only start angle; per-sample angle must be interpolated from consecutive packets' start angles (`angle = start_angle(k) + (diff(k, k+1) / 40) × index`) — [LR001 protocol en](https://bucket-download.slamtec.com/1cb3edd319c0fee6922fc5962e7765e887eccc36/LR001_SLAMTEC_lidar_protocol_v1.0_en.pdf)
- HQ (Sensitivity) capsule: descriptor `A5 5A 0D 03 00 40 83` (781 bytes). Packet: sync_byte 0xA5; time_stamp 64-bit (µs); 96 × Node_hq (8 bytes each: angle_z_q14 u16, dist_mm_q2 u32, quality u8, flag u8); Crc32 (32-bit). angle = angle_z_q14 × 90.0 / 16384.0; distance = dist_mm_q2 / 4 mm; quality 0–255; S = flag & 0x1 — [S2E protocol v1.0 cn](https://bucket-download.slamtec.com/29ed73b84370f1ff1e3c09022b79976b46c6558f/SLAMTEC_rplidarkit_protocol_S2E_v1.0_cn.pdf)
- Timestamps: Manual states "The Sensitivity mode can output range, angle and intensity information, as well as internal lidar time stamps for each 96 point cloud data" — [S2E user manual v1.0 en](https://bucket-download.slamtec.com/5350555d005bfd7a8685fcea6e80e9edb764adb1/SLAMTEC_rplidarkit_usermanual_S2E_v1.0_en.pdf). The SDK exposes `grabScanDataHqWithTimeStamp(..., sl_u64& timestamp_uS)` — [sl_lidar_driver.h](https://raw.githubusercontent.com/Slamtec/rplidar_sdk/master/sdk/include/sl_lidar_driver.h). The timestamp is the lidar's internal clock, not synchronized to host time.
- Scan modes: "The RPLIDAR S2E supports three scan modes" (Standard, DenseBoost, Sensitivity as in the protocol doc table) — [S2E user manual v1.0 en](https://bucket-download.slamtec.com/5350555d005bfd7a8685fcea6e80e9edb764adb1/SLAMTEC_rplidarkit_usermanual_S2E_v1.0_en.pdf). Manual says "For SDK, please refer to startScanExpress and grabScanDataHq".
- Motor speed: RoboStudio "Adjust Motor Speed" dialog; the manual shows 10.07 Hz (604 rpm) default and an example of 15.14 Hz. SDK `checkMotorCtrlSupport`, `setMotorSpeed` ("The function will stop scan if speed is DEFAULT_MOTOR_SPEED"). Protocol MOTOR_SPEED_CTRL 0xA8 takes Rpm u16; rpm = 60 / T where T is the interval between S=1 nodes — [S2E user manual v1.0 en](https://bucket-download.slamtec.com/5350555d005bfd7a8685fcea6e80e9edb764adb1/SLAMTEC_rplidarkit_usermanual_S2E_v1.0_en.pdf); [sl_lidar_driver.h](https://raw.githubusercontent.com/Slamtec/rplidar_sdk/master/sdk/include/sl_lidar_driver.h); [S2E protocol v1.0 cn](https://bucket-download.slamtec.com/29ed73b84370f1ff1e3c09022b79976b46c6558f/SLAMTEC_rplidarkit_protocol_S2E_v1.0_cn.pdf)
- Abnormal state: "When the scan core or the laser power works abnormally, the scan core will enter protection mode... please send restart command to reset the scan core" — [S2E user manual v1.0 en](https://bucket-download.slamtec.com/5350555d005bfd7a8685fcea6e80e9edb764adb1/SLAMTEC_rplidarkit_usermanual_S2E_v1.0_en.pdf). Protocol timing: after RESET wait ~1 s; after STOP wait 100 ms; ~2 ms recovery before SCAN referenced in the state-machine figure (partially unreadable) — [S2E protocol v1.0 cn](https://bucket-download.slamtec.com/29ed73b84370f1ff1e3c09022b79976b46c6558f/SLAMTEC_rplidarkit_protocol_S2E_v1.0_cn.pdf)
- SDK UDP channel implementation: `UdpChannel` uses a connected-style datagram socket (`setPairAddress`) to ip:port; `waitForData` is a plain socket wait; no keepalive or heartbeat messages are sent by the SDK channel code — [sdk/src/sl_udp_channel.cpp](https://raw.githubusercontent.com/Slamtec/rplidar_sdk/master/sdk/src/sl_udp_channel.cpp)

- S2E protocol doc and LR001 doc are marked LPX T1 / LIDAR "S" series; GET_LIDAR_CONF table lists T1M4 modes at 60000 sps alongside S2, so field values for S2E should always be read from the device, not hard-coded.

### Inferences
- UDP is connectionless: there is no handshake in the docs, so "connection" is just "device is streaming after receiving EXPRESS_SCAN". A pure TypeScript client (Node `dgram`) is feasible: bind a local UDP socket, send `A5 20`/`A5 82 05 ...`, read datagrams, parse by descriptor type 0x81/0x82/0x83. The SDK's own UDP channel adds nothing beyond a datagram socket.
- No heartbeat is documented. Disconnect handling must be implemented by the driver: a receive-timeout watchdog (no packet for N × scan period), then STOP/RESET/restart scan, resend GET_HEALTH. The "what happens on cable unplug/replug" behaviour (does it keep scanning, does it need a new scan command) is not documented and should be tested on the real unit.
- HQ mode is best for touch: it has an intensity/quality byte and CRC32, a per-packet µs timestamp (usable to time-align four independent sensors only relative to each sensor's own clock), and explicit per-sample angles. Dense mode saves bandwidth but "sacrifice[s] signal quality" and requires start-angle interpolation.
- Multiple S2E on the same subnet: nothing in the documents forbids it, but all units ship at the same default 192.168.11.2, so each must be configured individually (one at a time on an isolated link) with a unique static IP before joining the PoE switch. Not verified on hardware.
- Bandwidth: HQ 781-byte packets × 32000/96 ≈ 333 packets/s ≈ 260 KB/s (~2.1 Mbit/s) per sensor, well within 100 Mbit/s even for four sensors (derived).

### Gaps
- Official English S2E protocol PDF: the English S2E "protocol" file was not located; only the Chinese S2E protocol v1.0 and the generic English LR001 protocol v1.0 were read.
- Heartbeat/keepalive, cable-disconnect/reconnect behaviour, UDP discovery wire format (mDNS service name), multi-unit behaviour, IP-config wire command bytes (the command for `setLidarIpConf`), MAC address command: not in the documents read. The `sl_lidarprotocol_codec.cpp` in the SDK could be inspected for the exact command constants.
- Whether S2E has an "ultra dense" mode: the SDK's recent commit "Bugfix: Get incorrect sample delay offset in ultradense mode" (2023-10-26) concerns that mode on other models; the S2E documents list three modes only, so not applicable to S2E as far as verified.

## 5. Integration options for Electron/Node on Windows

### Takeaway
No source gave direct evidence comparing the three architectures for S2E. Based on the protocol facts, a pure TypeScript UDP client or a C++ sidecar are both feasible; the SDK is thin over a datagram socket, so wrapping it brings little benefit while adding native-build and GPL/BSD licensing surface.

### Cited Findings
- UDP channel in the SDK is a thin wrapper around a datagram socket with no keepalive — [sl_udp_channel.cpp](https://raw.githubusercontent.com/Slamtec/rplidar_sdk/master/sdk/src/sl_udp_channel.cpp)
- SDK v2.1.0 moved to "async fetching and decoding" for performance — [ReleaseNote v2.1.0](https://raw.githubusercontent.com/Slamtec/rplidar_sdk/master/docs/ReleaseNote.v2.1.0.md)
- Slamtec "highly recommends" using the Public SDK to manipulate work modes rather than raw protocol — [LR001 protocol en](https://bucket-download.slamtec.com/1cb3edd319c0fee6922fc5962e7765e887eccc36/LR001_SLAMTEC_lidar_protocol_v1.0_en.pdf)
- Windows build of SDK requires VS2010/VS2019 solution files (`workspaces/vc14`) — [GitHub page](https://github.com/Slamtec/rplidar_sdk)

### Inferences
- (a) N-API addon: no existing binding; would require node-gyp/cmake-js plus Electron ABI rebuilds (electron-rebuild) and a vc14 build of the SDK; a crash in native code takes down the main/utility process; benefit is reuse of the official parsing; trade-off is highest build/maintenance complexity.
- (b) Pure TypeScript over `dgram`: HQ packet is 781 bytes at ~333 packets/s per sensor, trivially handled in Node (a worker thread or utility process per sensor avoids event-loop jitter); full control of timeouts/reconnect; risk is protocol gaps (IP-config, undocumented behaviours) that the SDK has handled; clean licensing (clean-room from Slamtec's published PDF).
- (c) Sidecar (C++ SDK-linked or Rust/Python) streaming over local UDP/WebSocket: crash isolation and independent restart; extra IPC latency (sub-millisecond on loopback; negligible versus 100 ms scan period); extra packaging (an additional exe in the installer); if it links the SDK, the BSD-2 attribution and avoidance of the GPLv3 demos applies.
- Given 4 sensors and ~2 Mbit/s each, a hybrid is reasonable: pure-TS driver as primary (with an Electron `utilityProcess` per sensor for isolation) and the official SDK/RoboStudio as a reference for testing.

### Gaps
- No benchmarks, blog posts or case studies on Electron + RPLIDAR were found. Trade-offs above are reasoned, not sourced.

## 6. Field issues for touch walls

### Takeaway
Slamtec itself publishes a touch-wall workflow (Interactive Toolkit) that places the lidar directly above or below the interactive area (about 50 cm offset typical) and outputs TUIO; it requires merge distance > 30 mm. No S2E-specific field reports (crosstalk, glass, projection paint, dark clothing) were found in forums or application notes, so those risks are unverified for S2E.

### Cited Findings
- Mounting guidance: "the LIDAR is usually installed in the interactive screen area directly above or directly below the position of about 50cm, support customized settings"; set Size (mm) and Bias for the lidar's location; coordinate flip/rotate supported — [Interactive Toolkit manual](https://wiki.slamtec.com/download/attachments/83066883/RPLIDAR%20Interactive%20Toolkit%20Instruction%20Manual%20-%20V1.1.pdf?api=v2)
- Filter: "Point will move smoother with filter on at the cost of latency. The Q and R value are used to balancing smoothing and jelly" and the lag "is much smaller than the latency of your display" — [Interactive Toolkit manual](https://wiki.slamtec.com/download/attachments/83066883/RPLIDAR%20Interactive%20Toolkit%20Instruction%20Manual%20-%20V1.1.pdf?api=v2)
- Lidar installed "directly above" a wall region and mixed merging: "Merge distance decide the minimum distance in mm between two objects if they need to be considered as different cursors. This number should be larger than 30" — [Interactive Toolkit manual](https://wiki.slamtec.com/download/attachments/83066883/RPLIDAR%20Interactive%20Toolkit%20Instruction%20Manual%20-%20V1.1.pdf?api=v2)
- Range falls with reflectivity: 30 m at 90% vs 10 m at 10% for S2/S2E — [Slamtec S2 spec page](http://www.slamtec.com/en/s2/spec). Thus dark clothing (low reflectivity) still detectable at the short ranges used for walls (a few metres).
- Scan-field flatness ±1.5° (plane tilt) — [Slamtec S2 spec page](http://www.slamtec.com/en/s2/spec)
- Temperature/warm-up: 2-minute pre-heat for best accuracy; operating -10 to 50 °C — [S2E user manual v1.0 en](https://bucket-download.slamtec.com/5350555d005bfd7a8685fcea6e80e9edb764adb1/SLAMTEC_rplidarkit_usermanual_S2E_v1.0_en.pdf)
- Multi-lidar crosstalk: general lidar literature (Ouster docs; patents) recommends physical barriers, avoiding direct face-to-face alignment, or phase-locking with azimuth windows; a RobotShop thread about two RPLIDAR A3 units on one robot reports differences between units with one reply mentioning possible mutual interference (unconfirmed) — [Ouster multi-sensor synchronization](https://ouster.com/sensor-docs/fw-user-manual/multi-sensor-synchronization); [RobotShop forum](https://community.robotshop.com/forum/t/inconsistency-between-two-rplidar-a3-units/79248)
- Slamtec's marketing claims S2-series can detect transparent glass and mirrors and 80,000 lux ambient immunity (vendor claims, unverified) — [Core Electronics listing](https://core-electronics.com.au/rplidar-s2l-360-degree-laser-range-scanner-18m-range-2d-point-cloud-map-80000-lux-light-resistance-ip65-high-safety-for-human-eye.html.md)
- Community tutorials exist for interactive walls with RPLIDAR A1 + TouchDesigner (monitor-as-touchscreen series on alltd.org) and a Reddit thread suggests small lidars on a wall for projected touch — [alltd.org](https://alltd.org/?p=52053); [Reddit mirror](https://red.127.pp.ua/r/TouchDesigner/comments/1k50t9m/touch_interface_on_a_projected_wall) (anecdotal)

### Inferences
- With a top-center mount and the scan plane parallel to the wall a few cm away, the near-wall plane is within the S2E's 5 cm blind range only if the plane distance is under 5 cm from the sensor housing's optical centre in the radial direction, which is not a concern for points far down the wall, but the first few centimetres below the sensor at x≈0 are unusable: touches directly under the sensor would be in the blind zone (derived, needs on-site test).
- Four lidars on four walls of a rectangular room will have their scan planes facing each other across the room; because each plane is parallel to its own wall and a few cm in front of it, planes of opposite walls are parallel and offset by the room size, so beams from one sensor graze the opposite wall's plane only if the planes intersect (corner regions). Crosstalk risk is highest at corners where adjacent walls' planes cross and when a person blocks nothing. This is inference; no S2E crosstalk data was found. Mitigations: slight different heights/tilts for each wall, different motor speeds so scans de-synchronize, software rejection of returns at the angle where another sensor sits.
- Mixed pixels (edge artifacts) and reflections on glossy projection paint were not documented for S2E; must be tested on site. Filtering using the HQ-mode quality value and a minimum-cluster-size can help.
- Vibration/dropouts: nothing sourced; UDP packet loss on a PoE switch is unlikely at ~2 Mbit/s but the driver should detect gaps (HQ CRC32 and S flag).
- Firmware upgrade tool: not found in documents read (RoboStudio likely, unverified).

## 7. Implications of 10 Hz and scan-rate options

### Takeaway
Nominal 10 Hz means a 100 ms sampling period per sensor (a fresh position every 100 ms, plus up to one revolution of age on the touch point depending on the angle at which the hand is swept); the motor speed is adjustable (15 Hz shown in the manual), at the cost of angular resolution. Slamtec's own toolkit applies filtering, accepting extra latency.

### Cited Findings
- Scan rate 10 Hz, sample rate 32000/s, angular resolution 0.1125° — [Slamtec S2 spec page](http://www.slamtec.com/en/s2/spec)
- Motor speed adjustable in RoboStudio/FrameGrabber (Rpm); the dialog example shows 15.14 Hz; default about 10.07 Hz (604 rpm) — [S2E user manual v1.0 en](https://bucket-download.slamtec.com/5350555d005bfd7a8685fcea6e80e9edb764adb1/SLAMTEC_rplidarkit_usermanual_S2E_v1.0_en.pdf)
- Interactive Toolkit motor speed: "For S series, this number is in RPM" and the displayed FPS "is not strictly equals to the actual speed of Lidar motor" — [Interactive Toolkit manual](https://wiki.slamtec.com/download/attachments/83066883/RPLIDAR%20Interactive%20Toolkit%20Instruction%20Manual%20-%20V1.1.pdf?api=v2)
- Toolkit filter: smoother at cost of latency — [Interactive Toolkit manual](https://wiki.slamtec.com/download/attachments/83066883/RPLIDAR%20Interactive%20Toolkit%20Instruction%20Manual%20-%20V1.1.pdf?api=v2)

### Inferences
- Sample rate is fixed at 32,000 sps (per spec); raising rotation speed to 15 Hz gives about 2,133 samples per revolution, i.e. about 0.169° per sample (derived: 32000/15), a 50% coarser angular resolution; lateral spacing at 3 m would become about 8.8 mm instead of 5.9 mm. 15 Hz yields 66.7 ms period. The trade-off also includes motor wear and possibly noise; the datasheet range of allowed rpm was not found.
- Latency budget: average age of a measurement is half a revolution (50 ms at 10 Hz) plus network/processing; a fast swipe of 1 m/s moves 100 mm between scans, so tracker association needs a velocity-aware (e.g. Kalman / predictive) gate; Slamtec's toolkit exposes "Max speed" (pixel distance per frame) and "lifetime" parameters for the same reason.
- Using 4 sensors, scans of different walls are not synchronized (each has its own clock), so the fusion layer should timestamp on arrival and use the S2E HQ timestamp only for per-sensor jitter correction.

### Gaps
- Min/max allowed RPM for S2E and effect on accuracy/range: not found.
- Measured end-to-end latency of S2E over UDP: not found.
